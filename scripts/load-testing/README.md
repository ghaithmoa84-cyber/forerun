# FAWRUN Load & Concurrency Testing Suite (NestJS Backend)

حزمة سكربتات خفيفة لاختبار الحمل والتزامن (Load & Concurrency Testing) مخصصة للتحقق من صمود الباكند، حراسات التزامن (Concurrency Guards)، والنزاهة المالية (Financial Ledger Invariants)، تمهيداً لتشغيلها على بيئة Railway بعد استقرارها.

> ⚠️ **تنبيه أمني وعملياتي صارم:**
> السكربتات في هذا المجلد تم إعدادها وتجربتها **محلياً فقط**.
> **ممنوع منعاً باتاً تشغيل أي سكربت على بيئة الإنتاج أو حتى بيئة Railway الحالية دون تأكيد وموافقة بشرية صريحة ومنفصلة مسبقاً.**

## 2. توثيق السيناريوهات والمتغيرات والنتائج المتوقعة

### السيناريو 1: إنشاء طلبات متزامنة (`01-concurrent-orders.js`)
* **الهدف:** إرسال دفعات طلبات متزامنة (10، 30، 50 طلباً) في نفس الثانية تقريباً من حسابات عملاء مختلفة لقياس معدل النجاح وزمن الاستجابة ومنع تكرار أرقام الطلبات أو حدوث تعارض في المعاملات (Transaction Deadlocks).
* **المتغيرات القابلة للتعديل:**
  - `TARGET_URL`: عنوان الخادم المستهدف (الافتراضي: `http://localhost:3000`).
  - `--concurrency=<N>` أو `CONCURRENCY=<N>`: عدد الطلبات المتزامنة (10، 30، 50).
* **كيفية التشغيل:**
  ```bash
  node scripts/load-testing/01-concurrent-orders.js --concurrency=10
  node scripts/load-testing/01-concurrent-orders.js --concurrency=30
  ```
* **النتائج المتوقعة استناداً لكود المشروع:**
  - معدل نجاح 100% بحالة `201 Created`.
  - كل طلب يحصل على `orderNumber` فريد ومتسلسل بصيغة `FW-XXXXXX` ناتج من تسلسل PostgreSQL الذري (`seqNumber`) داخل معاملة DB.
  - خلو تام من أخطاء السيرفر (`500 Server Errors = 0`).

---

### السيناريو 2: تسليم طلبات متزامنة وفحص الدفتر المالي (`02-concurrent-deliveries.js`)
* **الهدف:** اختبار حراسة التزامن ومفتاح عدم التكرار (Idempotency Key) المضافة حديثاً في عملية التسليم `deliverOrder` (`runner-orders.service.ts`) عبر إطلاق طلبات تسليم متزامنة من مناديب مختلفين بالتوازي مع محاولات سباق متزامنة (Race attempts) بنفس المفتاح.
* **المتغيرات القابلة للتعديل:**
  - `TARGET_URL`: عنوان الخادم المستهدف.
  - `--concurrency=<N>` أو `CONCURRENCY=<N>`: عدد الطلبات المجهزة للتسليم (الافتراضي: 5).
* **كيفية التشغيل:**
  ```bash
  node scripts/load-testing/02-concurrent-deliveries.js --concurrency=5
  ```
* **النتائج المتوقعة استناداً لكود المشروع:**
  - استجابة ناجحة `200 OK` لجميع الطلبات الأساسية وتكراراتها المتطابقة (Idempotent replay).
  - **النزاهة المالية الصارمة (Invariants):**
    1. تسجيل **قيد مالي وحيد** في جدول `LedgerEntry` من نوع `ORDER_FEE_TOTAL` لكل طلب مُسلّم (استناداً للقرار المعماري D25).
    2. قيمة القيد المالي موجبة وتطابق تماماً `order.totalFee`.
    3. عودة حالة المندوب في جدول `Runner` إلى `AVAILABLE` لمنع بقائه عالقاً في `ON_MISSION`.
    4. زيادة عداد العميل `completedOrders` وقيمة `totalFeesPaid` مرة واحدة فقط لكل طلب.
    5. خلو تام من أي أخطاء `500`.

---

### السيناريو 3: حراسات التنازع على نفس المورد (`03-concurrent-conflicts.js`)
* **الهدف:** مهاجمة نفس المورد (نفس الطلب، نفس المتجر) بـ 10 طلبات متزامنة في نفس الميلي ثانية من عدة اتصالات حقيقية للتأكد من حراسات التزامن المضافة حديثاً في `cancelOrder` و `deleteOrderStore`:
  - **الجزء 3A:** محاولة إلغاء نفس الطلب في ذات اللحظة من طرف العميل (`DELETE /customer/orders/:id`) والإدارة (`PUT /admin/orders/:id/cancel`).
  - **الجزء 3B:** محاولة حذف نفس المتجر قيد الانتظار (`DELETE /runner/orders/:id/stores/:storeId`) من عدة اتصالات مندوب في نفس الميلي ثانية.
* **المتغيرات القابلة للتعديل:**
  - `TARGET_URL`: عنوان الخادم المستهدف.
  - `--attempts=<N>`: عدد المحاولات المتزامنة المتصارعة على المورد الواحد (الافتراضي: 10).
* **كيفية التشغيل:**
  ```bash
  node scripts/load-testing/03-concurrent-conflicts.js --attempts=10
  ```
* **النتائج المتوقعة استناداً لكود المشروع:**
  - في كلا الجزأين (3A و 3B): **يفوز طلب واحد فقط** ويحصل على `200 OK`.
  - كافة المحاولات المتزامنة الأخرى (9 طلبات) يتم صدّها فوراً بالحراسة وترجع إما `409 Conflict` بنص `ORDER_STATUS_CHANGED_CONCURRENTLY` أو `422 Unprocessable Entity` (للمتجر المحذوف مسبقاً).
  - خلو تام من أخطاء السيرفر `500` أو تلف البيانات التابعة.

---

### السيناريو 4: اتصالات WebSocket متزامنة (`04-websocket-connections.js`)
* **الهدف:** فتح 50 إلى 100 اتصال متزامن بنطاق Socket.IO (`/orders`) باستخدام توكنات مصادقة صالحة، وإبقاؤها مفتوحة لعدة ثوانٍ لاختبار استقرار الـ Handshake والذاكرة.
* **المتغيرات القابلة للتعديل:**
  - `TARGET_URL`: عنوان الخادم المستهدف.
  - `--connections=<N>` أو `WS_CONNECTIONS=<N>`: عدد الاتصالات المتزامنة (50 أو 100).
  - `--duration=<N>` أو `WS_DURATION=<N>`: مدة الإبقاء على الاتصالات بالثواني (الافتراضي: 5 ثوانٍ محلياً، 10-30 على Railway).
* **كيفية التشغيل:**
  ```bash
  node scripts/load-testing/04-websocket-connections.js --connections=50 --duration=5
  node scripts/load-testing/04-websocket-connections.js --connections=100 --duration=10
  ```
* **النتائج المتوقعة استناداً لكود المشروع:**
  - نجاح 100% في مصافحة Socket.IO لجميع الاتصالات عبر بروتوكول WebSocket المباشر.
  - انضمام كل عميل لغرفته المخصصة (`customer:${userId}` أو `runner:${userId}`).
  - انعدام انقطاع الاتصالات (`0 drops`) أثناء فترة الانتظار، مع إغلاق سلس (Graceful disconnect) عند الانتهاء.

---

### السيناريو 5: خط الأساس لنقاط القراءة (`05-read-baseline.js`)
* **الهدف:** قياس سرعة الاستجابة القصوى والإنتاجية (req/s) باستخدام أداة `autocannon` المدمجة على نقطتين شائعتين:
  1. نقطة عامة مكوشة في الذاكرة: `GET /api/v1/banners/active`.
  2. نقطة محمية تتطلب مصادقة واستعلام قاعدة بيانات: `GET /api/v1/customer/orders`.
* **المتغيرات القابلة للتعديل:**
  - `TARGET_URL`: عنوان الخادم المستهدف.
  - `--duration=<N>` أو `BENCH_DURATION=<N>`: مدة الاختبار بالثواني (الافتراضي: 5 ثوانٍ).
  - `--connections=<N>` أو `BENCH_CONNECTIONS=<N>`: عدد الاتصالات المتزامنة (الافتراضي: 10 اتصالات).
* **كيفية التشغيل:**
  ```bash
  node scripts/load-testing/05-read-baseline.js --duration=5 --connections=10
  ```
* **النتائج المتوقعة استناداً لكود المشروع:**
  - على `/banners/active`: إنتاجية تتجاوز 1,400 req/s بزمن استجابة p50 = 6ms، مع صد ما يزيد عن 120 طلب/دقيقة عبر معدل التدفق المحدد في الكود (`@Throttle limit: 120`).
  - على `/customer/orders`: إنتاجية تتجاوز 700 req/s بزمن استجابة p50 = 12ms، مع صد ما يزيد عن 300 طلب/دقيقة عبر معدل التدفق المحدد في الكود (`@Throttle limit: 300`).
  - خلو تام من أخطاء الانهيار الداخلي (`0 network crashes`).

## 3. تعليمات التشغيل الفعلي اللاحق على بيئة Railway

عندما تستقر بيئة Railway ويُتخذ قرار صريح باختبار الحمل الفعلي عليها:

### الخطوة 1: طلب التأكيد البشري الصريح
> 🛑 **قاعدة أساسية:** لا تشغّل أي سكربت على Railway دون موافقة كتابية صريحة.

### الخطوة 2: ضبط متغير البيئة المستهدف
يمكن توجيه الحزمة بأكملها إلى بيئة Railway عبر تعيين متغير واحد فقط دون المساس بأي سطر كود:
```bash
# على PowerShell
$env:TARGET_URL = "https://backend-production-xxxx.up.railway.app"

# أو كأمر واحد عند التشغيل
TARGET_URL="https://backend-production-xxxx.up.railway.app" node scripts/load-testing/run-all.js
```

### الخطوة 3: التحقق من جاهزية حسابات الاختبار
تعتمد السكربتات على حسابات وهمية واضحة في النطاقات:
- المسؤول: `LOAD_TEST_ADMIN_WHATSAPP` و `LOAD_TEST_ADMIN_PASSWORD` (أو الحساب الإداري المعتمد في البيئة).
- العملاء: `0999900001` إلى `0999900050`
- المناديب: `0999800001` إلى `0999800010`

إذا كانت البيئة المستهدفة لا تسمح بإنشاء حسابات مباشرة من السكربت لغياب الوصول المباشر إلى قاعدة البيانات، يتم استخدام بيانات الاعتماد المجهزة في ملف `.fixtures.json`.

### الخطوة 4: التدرج في الحمل
1. ابدأ باختبار خط الأساس للقراءة أولاً للتأكد من زمن الوصول والـ Latency:
   ```bash
   TARGET_URL=https://... node scripts/load-testing/05-read-baseline.js --duration=5 --connections=5
   ```
2. شغّل سيناريو اتصالات WebSocket للتأكد من قدرة البروكسي على الحفاظ على Sockets المفتوحة:
   ```bash
   TARGET_URL=https://... node scripts/load-testing/04-websocket-connections.js --connections=20 --duration=10
   ```
3. شغّل اختبارات التنازع والتسليم المالي:
   ```bash
   TARGET_URL=https://... node scripts/load-testing/03-concurrent-conflicts.js --attempts=5
   TARGET_URL=https://... node scripts/load-testing/02-concurrent-deliveries.js --concurrency=3
   ```
4. ارفع الحمل تدريجياً لإنشاء الطلبات المتزامنة:
   ```bash
   TARGET_URL=https://... node scripts/load-testing/01-concurrent-orders.js --concurrency=10
   TARGET_URL=https://... node scripts/load-testing/01-concurrent-orders.js --concurrency=30
   ```
